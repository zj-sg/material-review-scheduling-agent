# 05 项目复盘

本复盘依据开发、修改与验证记录，描述项目中的工程问题和取舍，不将 AI 生成的经历写成未验证的个人经验。

## 最难的问题

第一是区分“工具调用流程存在”和“真实模型观察结果后调整动作”。早期离线模型只能证明业务工具可运行，时间冲突的程序中断也不能单独证明 ReAct。
最终保留真实模型的观察、工具调用 ID、公开 reason 与实际返回：同一个审核工具返回 passed 时选择查询，返回 needs_info 时选择补查。

第二是人工确认与实时占用的关系。用户接受的只是某个具体候选，等待期间占用可能变化。
因此恢复绑定当前中断 ID 和候选列表，保存事务中重查所选时间；失效时再次暂停，保留原始硬性要求，避免一次确认授权了另一时段。

第三是“保存成功”必须对应提交成功。只执行 INSERT 或模型说“已保存”不够。
服务在同一写事务内检查占用、写入并提交；注入写入后失败、提交失败和连接中断，验证回滚及已有草稿不被部分覆盖。

## 修正过的设计

初始八阶段方案包含版本历史、审批记录与复杂时间处理，超出笔试重点。按用户反馈收敛到单 Agent、北京时间、当前草稿和可复现示例。
之后按明确新增需求补 HTTP 与人工选择，没有恢复已删除的大型审批系统。

工具接入由手写协议与分发改为框架 @tool / bind_tools / ToolNode，业务校验仍由服务执行。
一次真实模型调用出现 ValueError，旧日志不足以判断原因，促使补充无效响应审计；没有把失败试次移除后宣称始终成功。

## 可复用的认识

- 确定性代码适合规则、时间计算、幂等和事务；模型适合根据工具反馈选择下一动作。
- Trace 应记录实际观察与动作，并标注模型/程序来源。公开的一句话依据可以解释动作，无需内部思维过程。
- 离线、HTTP Mock、真实工具执行和真实模型调用证明不同层面的事实，需要分开标记。
- 文档必须能在新环境指导安装，并引用仓库中的实际文件；仅有本机 .venv 或忽略目录里的结果不够交付。

## 下一步

优先扩大真实模型的风险、故障和多次冲突场景评测，分析失败率与调用成本；当前两条通过只证明这两条路径。
若实际部署需要多进程或重启恢复，再引入持久化检查点和身份权限；若对接真实素材平台，再增加可靠资料来源与授权核验。
在此之前保持题目范围，不为展示框架数量而引入多 Agent、前端或版本历史。
